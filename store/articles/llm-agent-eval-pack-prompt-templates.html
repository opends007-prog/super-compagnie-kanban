The LLM Agent Eval Pack: 25 Tested Prompt Templates with JSON Schemas & Python Runner

You've built an agent that can browse the web, write code, and call tools. It works in your demo. But when you run it against a real task list, it fails in ways you didn't predict: it hallucinates tool outputs, loops on the same error, or returns JSON that doesn't match your schema. You need a systematic way to find these failures before your users do.

This guide shows you how to build an evaluation harness for LLM agents using prompt templates, JSON schemas, and a Python runner. You'll get patterns you can copy directly into your own eval suite.

Why Agent Eval Is Different from LLM Eval

A single LLM call has one input and one output. An agent has multiple calls, tool invocations, and state changes. The failure modes multiply:

  • Tool call formatting errors — the model emits {"action": "search"} when your schema expects {"tool": "search"}
  • Premature termination — the agent stops after one step when the task needs three
  • Runaway loops — the agent repeats the same failing action without adapting
  • Context drift — the agent loses track of the original goal after several tool calls
  • Hallucinated tool results — the agent fabricates a response instead of calling the tool

Unit-testing individual prompts won't catch these. You need end-to-end evaluation that exercises the full agent loop.

The Three-Part Eval Structure

Every agent eval in this pack follows the same structure:

  1. Prompt template — the task definition with placeholders for variables
  2. JSON schema — the expected output structure for validation
  3. Python runner — the harness that executes the agent and scores results

This separation matters. You can swap prompts without touching the runner. You can add new schemas without rewriting prompts. And you can run the same test suite against different models to compare performance.

Building Your First Agent Eval

Start with a simple task: "Find the current price of a product and return it as a number."

Step 1: Define the Prompt Template

You are a shopping assistant. Find the current price of {product_name} at {store_url}.
Return the price as a number with no currency symbol.
If you cannot find the price, return null.

Keep the template minimal. The agent needs enough context to act but not so much that you're testing the model's ability to follow long instructions rather than its ability to use tools.

Step 2: Define the JSON Schema

{
  "type": "object",
  "properties": {
    "price": {"type": ["number", "null"]},
    "currency": {"type": "string", "enum": ["USD", "EUR", "GBP"]},
    "source_url": {"type": "string", "format": "uri"}
  },
  "required": ["price", "currency", "source_url"]
}

Your schema should be strict enough to catch malformed output but flexible enough to allow valid variations. If you require a source_url, the agent must provide evidence for its answer — this catches hallucinated prices.

Step 3: Write the Python Runner

import json
import jsonschema
from agent import run_agent

def evaluate_agent(task, schema, expected):
    result = run_agent(task)

    # Validate JSON output
    try:
        jsonschema.validate(result, schema)
        schema_valid = True
    except jsonschema.ValidationError:
        schema_valid = False

    # Check correctness
    correct = False
    if schema_valid:
        correct = (result.get("price") == expected["price"])

    return {
        "schema_valid": schema_valid,
        "correct": correct,
        "result": result
    }

This runner does two checks: does the output match the schema, and is the output correct? Both matter. An agent that returns valid JSON with the wrong answer is different from one that returns invalid JSON with the right answer.

The 25 Template Categories

The full pack covers 25 prompt template categories. Here are the five most critical ones for production agents:

1. Multi-Step Tool Use

Tests whether the agent can chain tool calls in sequence. The task requires at least three steps: search, filter, and extract.

2. Error Recovery

Presents the agent with a failing tool call and checks whether it retries with a different approach or gives up.

3. Ambiguous Input

Gives the agent a vague instruction and checks whether it asks for clarification or makes reasonable assumptions.

4. Output Formatting

Tests whether the agent can produce output in a specific format (JSON, CSV, markdown) consistently across multiple runs.

5. Long-Horizon Tasks

Requires the agent to maintain context over 10+ tool calls. Checks for drift and premature termination.

Scoring Metrics That Matter

Don't just track pass/fail. Track these metrics:

  • Schema compliance rate — what percentage of runs produce valid JSON?
  • Tool call efficiency — how many tool calls per successful task completion?
  • Error recovery rate — what percentage of failed tool calls lead to successful retries?
  • Latency — how long does the agent take to complete the task?
  • Cost per task — how many tokens does the agent consume?

These metrics reveal different problems. High schema compliance with low correctness means your prompts are good but your model is weak. Low schema compliance means your prompts need work. High tool call count with low success means the agent is flailing.

Running Evals in CI

Your eval suite should run on every code change. Here's a minimal GitHub Actions setup:

name: Agent Evals
on: [push, pull_request]

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install -r requirements.txt
      - run: python run_evals.py --suite production

The run_evals.py script loads all test cases, runs them through your agent, and fails the build if any critical test fails. You can set thresholds: "fail if schema compliance drops below 95%" or "fail if average tool calls per task exceeds 8."

Common Pitfalls in Agent Evaluation

Testing with the same data you trained on. Your agent will look great in evals and fail in production. Hold out a set of tasks you never use in development.

Ignoring variance. LLMs are non-deterministic. Run each test at least three times and report the distribution, not just a single pass/fail.

Over-fitting to your eval set. If you keep adjusting prompts until they pass your tests, you'll end up with prompts that work only on your tests. Add new test cases regularly.

Not testing edge cases. Empty inputs, extremely long inputs, and malformed tool responses will break agents in ways you won't predict. Test them explicitly.

A Worked Example: The Shopping Agent

Here's a complete eval case from the pack:

Task: Find the price of a "wireless mechanical keyboard" at a specific electronics store.

Expected behavior: The agent searches the store, finds the product page, extracts the price, and returns it as a number.

Common failure modes this test catches: - The agent returns a price from a sponsored ad instead of the product page - The agent returns the price in the wrong currency - The agent hallucinates a price when the product is out of stock

Schema:

{
  "type": "object",
  "properties": {
    "price": {"type": "number", "minimum": 0},
    "currency": {"type": "string", "pattern": "^[A-Z]{3}$"},
    "in_stock": {"type": "boolean"},
    "product_url": {"type": "string", "format": "uri"}
  },
  "required": ["price", "currency", "in_stock", "product_url"]
}

Scoring rubric: - 1.0: Correct price, correct currency, in_stock accurate, valid URL - 0.5: Correct price but missing or invalid URL - 0.0: Wrong price or invalid schema

This rubric rewards evidence. An agent that returns the right price with a source URL scores higher than one that returns the right price with no evidence.

Making Your Evals Actionable

The output of your eval suite should tell you what to fix. Group failures by pattern:

  • Prompt issues — the agent consistently misinterprets the task
  • Tool issues — the agent calls tools incorrectly or fails to use available tools
  • Model issues — the agent produces invalid JSON or hallucinates results
  • Context issues — the agent loses track of the task over multiple steps

When you see a pattern, fix the root cause. If the agent fails on ambiguous inputs, add clarification steps to your prompt. If it fails on schema compliance, add a validation step that retries with error messages.

The Bottom Line

Agent evaluation is not optional. It's the difference between shipping an agent that works in demos and one that works in production. The 25 templates in the pack give you a starting point, but the real value is the structure: prompt templates, JSON schemas, and a Python runner that you can adapt to your specific use case.

Start with five test cases. Run them daily. Add more as you find failures. Track your metrics over time. You'll catch problems before your users do, and you'll have the data to prove your agent is ready for production.
